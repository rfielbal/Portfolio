Projet pédagogique réalisé en binôme avec Vincent Rouget. La solution sépare un serveur source actif et un serveur de stockage passif. Elle produit une archive chiffrée, en contrôle l’intégrité et propose un parcours de restauration documenté.

ARCHITECTURE / DEUX SERVEURS, DES RESPONSABILITÉS DISTINCTES

Le parcours d’une sauvegarde.

  1. 01

    Exporter

    MariaDB → dump SQL

    Le serveur A prépare une copie de la base. Le fichier SQL temporaire sert uniquement au chiffrement.

  2. 02

    Chiffrer

    age → archive .sql.age

    Le contenu est chiffré avant son départ. Le serveur de stockage ne reçoit pas le dump SQL en clair.

  3. 03

    Transférer

    SFTP → serveur B

    Le transfert utilise un fichier temporaire ; le marqueur .ready distingue une archive complète.

  4. 04

    Vérifier / restaurer

    SHA-256 → base dédiée

    L’archive est récupérée et comparée à son empreinte. La restauration déchiffre puis importe dans la base prévue.

CHOIX TECHNIQUES

A pilote.
B conserve.

Le serveur A conserve la configuration, les clés nécessaires, le catalogue et la planification Cron à 02 h. Le serveur B joue le rôle de stockage SFTP. Cette séparation évite de confier au stockage la logique de sauvegarde ou la clé privée de déchiffrement.

Confidentialité ≠ intégrité

age protège le contenu ; SHA-256 détecte une modification par comparaison avec l’empreinte conservée. Une empreinte seule ne remplace ni le chiffrement ni la protection du catalogue.

Une restauration explicite

Le parcours de restauration récupère réellement l’archive distante, vérifie l’intégrité et cible une base dédiée. La documentation précise les prérequis des deux serveurs.

RÉALISATION & SUPPORTS

Les livrables du projet.

  • Export SQL puis chiffrement age avant transfert.
  • Stockage distant SFTP avec publication des fichiers complets.
  • Empreinte SHA-256 pour vérifier l’intégrité de l’archive.
  • Restauration vers une base dédiée, avec contrôle préalable.
  • Planification quotidienne à 02 h et commandes documentées.
